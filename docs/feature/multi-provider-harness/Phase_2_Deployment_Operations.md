## Installation and local update

Follow the shared `Target_Project_Deployment_Workflow.md` command route. Review root/context text and custom role/rule merges into an adaptations JSON map. Use `lifecycle.py init|update|build` (or the executable PowerShell/Bash launchers) to print a plan. `project_root` excludes the repository Scrum corpus. For existing content, explicit hash-backed resolutions are required. A reviewed retirement has `after_sha256: null`; its path must be declared in the manifest and its shared successors verified. Project-owned content, unknown extra files and provider runtime histories cannot be retired. Runtime seeds only create missing files.

`migration.py --target <target> --provider <provider>` prints the old inventory and exact proposed text without writing the target. Rewrite references to shared destinations; do not copy historical sync bodies into the new shared sync owner. Surviving managed content that names retired paths is rejected in both plan and serialized-plan validation. Unknown stamped releases receive a safe conflict/inventory path; no unsupported auto-certification.

Apply the saved plan with `deployment.py apply --target <target> --plan <saved-plan.json>`, then `verify`. Immutable released sync uses `sync.py --repo <owner/repository>` and never fetches `/main` payloads. Source identity distinguishes local/snapshot and released-tag provenance. A receipt is the completion certificate. Compatibility stamps run after content/runtime verification, within the same backup journal.

Receipts distinguish the stock rendered digest (`stock_sha256`) from the installed digest and mark approved customizations (`adapted`). Repeats retain adapted instructions and rules when stock inputs are unchanged. Changed upstream stock requires a reviewed adaptation instead of silently reverting customization. Pre-correction receipts without stock metadata require an exact resolution when proposed bytes change; matching bytes remain idempotent.

Entrypoints preserve project prose and install a canonical `MT-AGENT-DEVKIT` marked routing section from the manifest asset. Before workflows, this section and the shared orchestrator require the Provider Contract, actual enabled tool identities, the target resolver CLI, and exactly the returned adapter and concrete bindings. Managed content lives under `.mt-agent-devkit/`, while runtime remains provider-local. Review legacy prose and rewrite active references before approving retirement; nested/flat instructions, old orchestrator names, mapped contexts and scripts retire only through individual exact resolutions after verified successor files and discovery.

## Interruption and rollback

`inspect` reports runtime hashes, active pipelines, lock and receipt. A mixed mode/version or nonterminal workflow blocks migration without state reset. Complete recovery backups/journal are persisted before the rootwide lock is atomically published as an exclusive link to a complete lock file. Failure before publication leaves no target lock or managed-file changes; interruption after publication has a complete recovery journal. The lock records the owning process identity and journal. The target filesystem must support exclusive same-directory hard links and atomic replacement (tested on this Windows NTFS host; Linux is exercised by CI). Unsupported publication fails closed before managed-file changes, cleans the temporary prepared lock on ordinary failure, and leaves the durable unreferenced journal available for inspection. There is no overwrite or nonexclusive fallback. Do not remove it to proceed. Read the journal's transaction ID and use `deployment.py resume|rollback --target <target> --transaction <transaction-id>`. Recovery rejects a live/ambiguous owner, changed files or changed receipts before changing recovery ownership. Both resume and rollback accept only the recorded receipt before/after identity; initial publication and restoration recheck that boundary. exact before-bytes restore created/replaced/retired files. The independent `.recovering` guard prevents simultaneous recovery. A stale guard requires explicit process/journal inspection; this tool does not guess that deleting it is safe.

These native limitations remain tracked by ST-000232 and require QA reporting and explicit PO acceptance; mechanical installation is not blanket native support.

Windows locks use process creation time; Linux uses `/proc` start identity. POSIX systems without `/proc`, including macOS, use locale-stable `ps -p <pid> -o lstart=`. Failed or ambiguous probes block recovery; only proven termination permits stale-owner recovery. The fallback is tested mechanically here; a macOS native filesystem/runtime pass remains unverified. All platforms still require exclusive hard-link publication and atomic replacement.
