# ST-000215 Acceptance Disposition Scenarios

## Scope and method

These frozen cases exercise the acceptance policy as a guidance walkthrough, not an external hostname integration or a native provider benchmark. The product is Markdown instructions; no production evaluator or service API is introduced. Independent QA must repeat the cases against the installed guidance and record its own verdict before merge.

Policy owner: `.mt-agent-devkit/rules/Story_Standard.md`, section 14. Active distribution owner: `.mt-agent-devkit/distribution/phase2/templates/rules/Story_Standard_template.md`. Consumers: QA Bootstrap/view, PO view/closure, Common credential gate, and Shared Pipeline Stages (Stage 3, Merge Procedure, Stage 4). Frozen legacy templates are unchanged.

For each case, read the current story fixture and per-AC evidence, assign individual verdicts, then attempt testing-pass, merge advancement, checkbox acceptance and done. Do not execute live GitHub mutations; record the permitted/forbidden decisions. Repeat for ordinary behavioral validation, the non-behavioral fast path and the QA-implementer/skipped-validator route. The latter requires independent PO per-AC validation before merge, rather than an invented QA-agent report.

## Frozen cases and implementer walkthrough

| Case | Inputs and action sequence | Observed policy disposition | Forbidden action |
|---|---|---|---|

Evidence identifies scope A and revision R1; independent QA report covers both; review/CI and merge confirmation are present. | AC1 PASS, AC2 PASS; testing-pass and merge allowed after existing gates; PO may accept both and close after confirmed merge. | Acceptance before merge or independent verification. |

| TC-03 Executed failure | AC1 passes; the actual AC2 hostname request executes and returns an unexpected response, with captured evidence. | AC2 FAIL. Record observed failure and request correction; block sign-off/advancement. An environmental explanation does not turn the failing check into PASS. | Classifying an observed wrong result as merely unperformed, or accepting despite failure. |
| TC-04 Approved tracked split | Start with TC-02. ## Evidence and limits

Implementer walkthrough: each disposition above follows the central verdict table, evidence gate or ordered tracked-split sequence. Universal pipeline pre-checks precede route-specific sign-off/merge/closure actions. Role/common consumers load the same authoritative section before acting. These are scenario traces against the authored instructions; they do not claim an independent agent, external system or all three native provider runtimes executed.

Mechanical deployment validation must render/install the repository profile in all six provider/mode layouts, compare the installed central policy bytes and check consumer references/gate placement. Existing aggregate deployment tests cover install/update/customization/runtime preservation; bundle `--check` guards generated assets and hashes. Native interpretation and independent per-AC QA remain separate evidence gates.
