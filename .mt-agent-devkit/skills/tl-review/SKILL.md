# TL Review

**Requires:** `pr-review` (shared reviewer procedure; load it first), `clean-code` (script changes), `credential-gate` (credential evidence)

You are the merge gate: no PR merges without your explicit approval. You cannot approve your own work; seek Developer peer review.

## 1. Reviewer Gate (before approving)

Pending CI follows `pr-review` step 3 (ci-watch, exact head, strict mode). Tick each before any approval:

- [ ] All CI checks on the PR have **finished**.
- [ ] No CI check is **failed**.
- [ ] **Zero checks reported is not passing evidence.** Apply the explicit zero-check exception in `Shared_Pipeline_Stages.md` Merge Procedure: record suppression/path eligibility, prior SHA/current head and the complete changed-file scope. A helper prior candidate stays NO RUN until that evidenced decision; no prior success or missing evidence is silently waived.
- [ ] The review criteria below pass.

## 2. Review Checklist (TL-only, on top of `pr-review`)

- For long local verification use `.mt-agent-devkit/contracts/Local_Verify.md` (local-verify): the full required command, selected provider bindings and a new run ID. Launch once; resume only supported waits on that identity. Missing completion is not success. Keep provider-local logs and independent verification gates.
- **Dependency pin:** a changed or new version pin must be actually resolvable, not only present in a local cache.
- **Resume-rule completeness (state-file or pipeline stories):** a new state field, status value or step in a resumable workflow needs an explicit resume branch for every value its write rules can produce. A new terminal or interrupted state with no branch silently falls into the nearest existing one.
- Verify compliance with the approved implementation design, and template structure completeness.
- **Script changes only:** verify the `clean-code` skill for `.sh` and `.ps1` scripts.
- **UI Prototype PRs** (only for a repo generated by Build Software's UI-bearing companion-repo convention): apply `.mt-agent-devkit/rules/UI_Prototype_Rules.md` before approving. Not applicable to the devkit's own repo.
- **Approve** by PR comment when all criteria pass; leave blocking comments if not. Change requests and notices: `pr-review` steps 5-7.

## 3. CI/Workflow Stories (Technical Scope is `.github/workflows/**` only)

Use this checklist instead of section 2:

- Gate-logic correctness (job-level vs step-level `if`).
- Secret and credential scope: no wider access than the job needs.
- Blast radius: no unrelated job or trigger changes behavior.
- Rollback safety: revertible without side effects.
- The `pr-review` CI gate (executed, head SHA, red-check diagnosis) still applies.

Skip naming, cross-reference correctness, template structure completeness and clean-code review.

## 4. Documentation and Template Stories

Focus on `pr-review` stale-reference, section-completeness and deleted-file criteria, plus:

- **Accuracy:** the template or workflow reflects the intended agent behavior.
- **Backward compatibility:** existing target projects that ran `init project` keep working after `sync devkit`.
