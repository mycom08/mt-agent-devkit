- Bug Reproduction Pre-Flight (ST-000027, `Shared_Pipeline_Stages_Shared_template.md`): runs ahead of Stage 0, github-mode detection is the `bug` label; strict mode has no label mechanism so detection is the presence of a populated `## Reproduction` section in the story MD instead (mirrors the "no free-text parsing, check a structured field" rule already used for `Repro Command` itself). "Tooling absent" (AC2) has no separate heuristic — it's inferred from the shell reporting the invoked command/binary itself missing when `Repro Command` is actually run, collapsing into the same skip path as an absent/`unknown` `Repro Command`. `Repro Skipped:` state-file field persists across per-story overwrites *within* a run only (same carry-forward as `Observations:`), reset by deleting the state file at run end — a later `continue sprint` always re-attempts.
- Adding an Nth **split workflow** file (ST-000028, `Refine_Prototype_Workflow`) touches the same kind of hardcoded-count ripple as adding an Nth rules file (see the ST-000021/ST-000023 entries above), but across a different file set — none of these are named in a typical story's AC/Technical Scope: `scaffold_mechanical.sh`'s `SPLIT_WORKFLOWS` bash array; `Init_Project_Workflow.md` (5 occurrences of the "9 workflow files"/"7 split" count + the "Split candidates" bullet list); `Update_Project_Workflow.md` (2 lists: "Split candidates" + "Expected files — workflows/"); `Sync_Devkit_Workflow_template.md` (3 spots: "Split candidates", "Applies to all N files", "Expected files — workflows/") **plus its working mirror** `.claude/agents/working/workflows/Sync_Devkit_Workflow.md`; `Build_Software_Workflow.md` (2 occurrences of the "9 verbatim rules files, all 9 workflow files" phrase). Grep `Refine_Sprint_Workflow` across `.claude/agents/` before starting a similar story — it appears in every one of these enumerations. Also: `scaffold_mechanical.sh`'s awk merge strips a split workflow's mode-specific thin-variant file down to **only** non-comment-only lines after line 1 — a thin variant whose entire body (beyond the `Shared logic:` pointer) is HTML-comment-only lines (`<!-- ... -->` alone on a line) contributes **nothing** to the deployed target-project file; verified empirically via a scratch dry-run of `scaffold_mechanical.sh`. Mode differentiation for a split workflow must therefore live inline in the **shared** file's own "**GitHub mode:**/**Strict mode:**" prose, never rely on the thin variant's comments actually reaching the target project.
- **Injected templates must never reference devkit-only local paths as executable steps (ST-000028 PR #87 round-1 review — CHANGES REQUESTED).** `.claude/agents/working/scripts/scaffold_mechanical.sh` and `.claude/agents/workflows/Build_Software_Workflow.md` exist only inside the devkit repo's own checkout — a target project's file tree has no `templates/` dir and never receives devkit-internal workflows (`Init_Project_Workflow.md` §"Never copy devkit-internal files"). An injected template (anything under `.claude/agents/templates/`) that tells the orchestrator to `bash .claude/agents/working/scripts/...` or "follow `Build_Software_Workflow.md`'s Stage N step X" dead-ends the first time a real target-project user runs it — `validate_templates.py` cannot catch this class of bug (it checks reference integrity *within the devkit's own repo*, where those paths do resolve). The fix pattern when a new template needs Build-Software-only automation: reuse `Sync_Devkit_Workflow_template.md`'s own fetch mechanism instead — it's injected into every target project and already documents fetching individual devkit template files over `{DEVKIT_SOURCE_URL}` (WebFetch + curl fallback) using `{DEVKIT_SOURCE_URL}`/`{DEVKIT_VERSION}` read from the target project's own `CLAUDE.md`. Restate exactly which files/tiers to fetch (a content list is fine to restate — TL confirmed a restated file list is not the problem); never restate or point at the *devkit-internal automation* that assembles them.
- **A `Loop Status`/pipeline-`Stage`-style resume field needs a branch for every value it can hold, not just the "still working" one (ST-000028 PR #87 round-1 review, CR-3).** `refine_prototype_state.md`'s original resume rule only branched on empty-path (→ Step 1) vs. `active` (→ Step 3); a state file left at `Loop Status: ended` (user already said stop, but the story-drafting handoff hadn't completed yet when the process died) fell through to no explicit rule and would have silently re-entered the iteration loop instead of resuming drafting. Generalizes the ST-000027 "warning-next-to-a-rule ≠ closing a resume gap" lesson: every distinct value a resume-governing field can hold needs its own explicit branch, checked when first designing the state file, not discovered later.
